# Decisions

Short records of gaps or conflicts in the spec and the choice made. Newest at the bottom.

## Phase 0 and 1

1. **Missed occurrences are derived, not stored.** The spec says a missed `let_go` occurrence is "recorded as missed". Nothing reads that record (there are no penalties), and it can always be recomputed from the schedule and `completions`, so no `missed` rows are written. If a feature needs them later, a view can derive them.
2. **Which occurrence a completion handles.** For fixed schedules, a completion dated `c` handles the latest occurrence dated on or before `c`. This keeps backdating pure and predictable ("done 2 days ago" on a daily task handles that day, not today).
3. **Floating `let_go` tasks roll forward.** If an `every_n_days` task with `let_go` isn't handled on its due day, the next due day is that day + N. Without this, a let-go floating task would never come back.
4. **Ranges in Appendix A become single values.** "Every 7–14 days" → every 10 days; "every 2–3 days" → every 2; "every 30–60 days" → every 45; "twice weekly" → Tue and Fri; "twice a year" → April and October; "seasonal" → the first month of each quarter (Mar, Jun, Sep, Dec); "yearly, fall" → October; plain "weekly" defaults to Saturday; "monthly" defaults to the first Saturday. Every value is editable after setup.
5. **Zone rotation only moves `weekly_on` tasks.** A weekly task whose location (or an ancestor) is mapped to weekdays uses those weekdays instead of its own. Daily, floating, monthly, and yearly tasks keep their schedules.
6. **`start_on` on tasks.** Tasks get a `start_on` date (defaults to the creation day in the household timezone). Fixed schedules have no occurrences before it, and a never-done floating task is first due on it.
7. **Backdating floor is the creation day.** "Never before the task existed" is the day `created_at` falls on in the household timezone, enforced in both `logic.ts` and a database trigger.
8. **Interim weekly meter.** The weekly meter is defined in credited XP, which arrives in Phase 2. Until then it sums effort × 10 for the household's completions this week (Mon–Sun), against `household_settings.weekly_target` (default 400). Phase 2 swaps the data source; the component doesn't change.
9. **Operators and settings reach the database through a function.** SQL can't read Netlify env vars, so `netlify/functions/sync-config` copies `OPERATOR_EMAILS`, `HOUSEHOLD_CREATION`, `HOUSEHOLD_STORAGE_MB`, and `OPERATOR_NAME` into `operators` and `app_config` with the service role. The app calls it once per session; it takes no input. The README also shows the one-line SQL alternative.
10. **Dev-only email login.** Production uses Google only. For local development, `supabase/config.toml` enables email/password and the sign-in screen shows a dev form only when `VITE_DEV_EMAIL_LOGIN=true` and the app runs in dev mode, so the seeded fictional users can sign in and household isolation is visible.
11. **Explicit `data-theme`.** A tiny external `theme-init.js` always sets `data-theme` to `light` or `dark` before paint, resolving `system` through `prefers-color-scheme` (and it keeps following it live). That lets each `tokens.css` have one dark block instead of two, and lets gallery tiles scope a theme and mode to any element.
12. **Extra tokens.** Beyond the shared token list, packs define `--on-secondary`, `--on-accent`, `--on-success`, `--on-warning`, `--on-danger` (text drawn on those fills) plus `--texture` and `--texture-opacity`. Colored text never uses a fill color directly, so the contrast test covers every text pairing the UI uses.
13. **Composite foreign keys for in-household references.** `tasks.location_id`, `tasks.assignee_id`, `completions.task_id`, `completions.done_by`, `completions.logged_by`, and `locations.parent_id` reference `(household_id, id)`. The database itself refuses a row that points into another household.
14. **Invite RPCs return status objects.** Invalid codes return `{ok: false, error}` instead of raising, so the failed attempt stays recorded for the rate limit (10 failures per user per hour).
15. **Realtime deletes.** Supabase Realtime can't filter DELETE events by column, and with RLS it sends only the primary key. The client subscribes to completion deletes without a filter and just invalidates its own queries, so another household's delete reveals nothing but a random id.
16. **Household settings are owner-only to change.** Spec 4.1 says the owner manages settings; members can change their own profile (name, avatar, color, theme, mode) only.
17. **Deed catalog added early as data.** `src/modules/rewards/deeds.ts` holds the Appendix B catalog now so the starter library's `deed_key`s are validated by a test. No reward logic exists until Phase 2.
18. **Local database tests without Docker images.** CI runs `supabase test db`. When the Supabase stack isn't available, `scripts/test-db.sh` starts a throwaway Postgres with pgTAP and a small shim (`supabase/tests/shim/`) that recreates the parts of Supabase the migrations use: roles, default grants, `auth.users`, `auth.uid()`, `auth.jwt()`, and the realtime publication.
19. **Operator page identifies households by a short id.** Sizes are shown per household with the first 8 characters of its id, never its name, so the operator page reveals nothing about what's inside.
20. **Scan floats over the tab screens only.** The Scan button floats above the tab bar on Today, Lists, Stuff, Plans, and Me, and hides on sub-pages so it never covers their own buttons (like Catch-up's submit). The five tabs keep the spec's order.
21. **Freshness bars never turn red.** They use success, accent, and secondary colors. A low bar is a nudge, not a warning, in keeping with "never shame".
22. **Removing a member uses a second tap, not undo.** Removal can't be undone from the client, so the button asks for a second tap instead of showing an undo toast. Everything else that can be reversed uses undo.
23. **Lists, Stuff, Plans, and Scan tabs show "coming soon" until their phases.** Module toggles already hide their tabs.
24. **The Me page keeps a reward placeholder.** It shows where levels, badges, and coins will go, with no numbers, until Phase 2.
25. **Privacy and Terms pages shipped early.** Google won't publish a sign-in app without privacy and terms links, so public `/privacy` and `/terms` pages ship now (spec 4.1 plans the Privacy page for Phase 7). They name the operator for signed-in visitors and speak generically otherwise. Self-serve export and deletion remain Phase 7, and the page says so.
